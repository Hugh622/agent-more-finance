## 執行摘要

這套系統已經不是「幾個 AI 幫手寫報告」的初級階段，而是具備角色分工、跨腿終審、唯一執行台賬、事件日曆、數據管道與判例庫的投研作業雛形。現有優勢是風控意識強、決策過程留痕、能承認資料缺口、亦能把衝突落成裁定；最大問題則是尚未把這些紀律轉成**可計算、可回放、可比較、可驗收**的系統。

因此，最重要的改進並非再增加更多規則或更多 AI 角色，而是依次補上四塊地基：

1. **可驗證性**：建立事件驅動回測、影子組合與試驗登記冊。
2. **可追溯性**：把台賬、訊號、資料快照、規則版本與模型版本連成同一條 lineage。
3. **可靠性**：把易失守護進程、單一資料源、非原子寫檔與無校驗和問題修正。
4. **獨立性**：讓不同研究腿不只「獨立寫報告」，亦使用不同資料源、不同方法與盲審程序。

若只做一件事，應先做「**Paper Trading v2 + Event Replay**」：每一個決策在產生時凍結輸入、規則和價格口徑；其後由同一執行引擎模擬成交、成本及退出，並按月計算結果。沒有這一層，規則愈多，主觀自由度反而愈大。

## 現狀判斷

### 已形成的能力

現有團隊把管理员、首席、宏觀、量化、全棧與通用助手分工，流程為派單、分腿、統合、歸檔及紙面執行；這比單模型直接出投資建議穩健得多。最近的年檢樣例亦真正執行了三方輸入、衝突裁決、唯一執行口徑和後續事件節點，而非只停留於概念描述。

紙面台賬有終身唯一編號、狀態、觸發條件、紙面成交假設及復盤標記，並清楚聲明目前空倉、沒有真實成交；這是一個好的安全邊界。團隊亦已建立「移出、留觀、禁止、新進」等狀態、倉位上限及事件窗，證明風險控制不是附錄，而是決策核心。

數據工程亦具備降級來源、manifest、缺口回填、自愈清單和 23×5 交易制度測試。靜態檢查顯示 30 個 Python 檔全部可由 AST 解析，23×5 模組所列 11 個測試亦全部通過。

### 成熟度評分

| 維度 | 現況 | 評分 | 主要原因 |
|---|---|---:|---|

| 風險紀律 | 有四閘、止損、事件窗、禁買 | 3.5/5 | 規則完整，但缺統計校準與風險預算 |
| 研究驗證 | 有紙面推演及復盤 | 1.5/5 | 缺事件驅動回測、樣本外驗證及基準比較 |

| 軟件質量 | 局部模組有測試 | 2/5 | 只有一個測試檔；主抓取器缺契約、整合及故障測試 |
| 知識治理 | 有檔案庫與版本標記 | 2.5/5 | 672 個檔案中存在 24 組精確重複，規則代碼散落 |

## 關鍵結構問題

### 規則多但未受驗證

團隊自己已指出，P0、C17 等規則目前依賴模擬驗證及紙面台賬，1.5 倍量能、三日二守等參數未有歷史統計優化。這是全系統最大的證據缺口，因為嚴格執行一條沒有正期望值的規則，只會把錯誤更一致地執行。

現有年檢可以把分歧清零，卻未回答以下問題：每項規則跨市場、跨波動 regime 的命中率是多少；獲利與止損的分布如何；相對簡單基準是否有增量；規則由多少次嘗試中挑選出來。聯儲模型風險框架把概念合理性、持續監控和 outcomes analysis／back-testing 列為驗證核心，並要求模型清單、問題追蹤與足夠詳細的文檔。[^14][^15]

此外，回測不能只做一次漂亮的歷史曲線。金融研究的多重測試很容易把隨機噪音選成「最佳策略」；Deflated Sharpe Ratio 正是為選擇偏誤、多重測試與非正態回報而設，PBO／CSCV 則用來估計某個回測被過度擬合的概率。[^16][^17][^18][^19]

### 多腿可能同源同錯

現在的「宏觀腿 × 量化腿 × 支援層」形式上獨立，但若底層共同讀取同一份騰訊 K 線、同一覆蓋矩陣、同一事件敘事，輸出之間並不是真正獨立。年檢中出現 XOM/CVX 區帶誤標、藥明代碼混淆等案例，正好證明「三份報告一致」未必等於三份獨立證據。

更好的安排是把分歧刻意制度化：資料腿只提供簽名快照與品質評分；量化腿不能看到宏觀結論；宏觀腿不能看到技術判定；紅隊負責尋找反證；首席只在各腿提交後解盲。SFC 亦要求在可行情況下把模型開發與驗證、批准及持續監察職能分隔。[^13]

### 台賬仍是文件

台賬已經做到唯一主檔及不刪歷史，但主體仍是 Markdown 表格。欄位目前沒有完整記錄 signal timestamp、decision timestamp、有效期、規則版本、資料版本、證據 URI、責任人、成本、R multiple、benchmark return、退出原因與事後歸因。

這會形成三個問題：無法精準回放當時可見資料；無法自動識別未來資料洩漏；無法分解「研究正確但成交差」與「研究本身錯誤」。最終應由資料庫或 append-only JSONL 作事實主檔，Markdown／HTML 只是由主檔生成的閱讀視圖。

### 數據可用但不可重現

補充包的 33 份 manifest 能解析，並記錄執行時間、結果、來源混合和部分降級資訊；但未見 sha256/checksum、schema version、git commit/code version、input hash、quality score 或 timezone 欄位。因此，團隊可以知道某天「跑過」，卻未必能證明今天重新跑出的是同一批輸入與同一版程式。

覆蓋矩陣有 212 行、8 欄，但出現大量空白欄位；空白未被明確區分為「不適用、未取到、未驗證、等待人工補錄」。這些狀態若不拆開，後續模型或 AI 很容易把缺失誤當正常值。

### 運維存在生產級缺口

現有環境沒有 OS 級調度器，依賴易失的常駐程序與心跳；三個月內發生四次死亡事故，其中一次跨 FOMC 週造成七天零排程。過往修復雖成功回填，但故障擴大的原因包括看門狗等待超時後退出、未拉起 scheduler，且 SPCX 守護不在原檢查清單。

核心寫檔目前直接 `to_csv` 或直接 `json.dump` 到目標路徑，未見「臨時檔 → fsync → 原子 rename」模式。程序在寫檔中途死亡時，讀者可能取得半截 CSV／JSON；單寫者原則只能減少競爭，不能解決崩潰一致性。

### 測試覆蓋嚴重失衡

23×5 腳手架的 11 個邊界測試全部通過，包括 DST、維護窗與多源收盤驗證。然而，在兩個工作區只發現一個測試檔，主 market_fetcher、儲存、降級鏈、scheduler、symbol mapping 和 manifest contract 沒有同級測試。

靜態掃描亦發現多處寬泛 `except Exception`，其中至少一處直接 `pass`；這未必表示程式錯，但會增加靜默降級與根因不可觀察的風險。應改成具體例外、結構化錯誤碼、重試預算、dead-letter queue 及失敗告警。

### 知識庫會逐步漂移

現有工作區有 672 個檔案、39 個顯式版本檔及 24 組精確重複內容；同一報告往往同時存在根目錄、研究檔案庫和 research_reports。短期這方便取用，長期會出現「哪份是 canonical」「修改了 A 卻漏了 B」「AI 搜到舊版」的問題。

規則代碼 C/R/N/D/K/W/G/P 在大量文件散落，與自評所指的複雜度問題一致。需要一份機器可讀的 Rule Registry，而非繼續靠檔名和人腦維持一致性。

## 優先改進藍圖

### P0：立即處理

| 改進 | 具體交付 | 驗收準則 |
|---|---|---|
| 憑證及秘密管理 | 輪換已入包 API key；環境變數或 Keychain 注入；日誌 token redaction；pre-commit secret scan | 歷史包、日誌及 Git 全掃描零真實密鑰；舊 key 已失效 |
| 排程外部化 | macOS `launchd`、獨立 supervisor 或雲端排程；每個 job heartbeat；失敗推送告警 | 殺死程序後 2 分鐘內拉起；漏跑 15 分鐘內告警；可演練 |
| 原子寫入 | tmp file、flush/fsync、schema 驗證後 rename；讀者只讀 `_SUCCESS` 完成批次 | 人為 kill 寫檔進程 100 次，不產生可見半檔 |
| Manifest v2 | 加 `run_id`、UTC/HKT timestamp、schema version、code commit、config hash、input/output sha256、source URL、row count、min/max date、quality status | 任一報告數字可追溯至檔案 hash 與程式版本 |
| 缺失狀態化 | 把空白拆成 `not_applicable`、`not_available`、`failed`、`manual_pending`、`verified` | 覆蓋矩陣不再有語義不明空白 |

秘密管理是最高 ROI 項目：補充包已清楚指出真實 Finnhub key 曾進入配置及錯誤日誌，應視為已暴露並輪換。此外，SFC 2026 年網絡安全要求強調權限最小化、異常監控、事件演練及快速修補。[^24][^25]

### P1：四週地基

#### 建立 Paper Trading v2

把「研究訊號」與「模擬成交」分開，建立以下核心表：

- `instrument_master`：永久 instrument_id、交易所、幣種、symbol history、corporate actions。
- `market_snapshot`：as-of timestamp、source、adjustment flag、timezone、hash。
- `signal`：signal_id、rule_id/version、方向、entry/exit 條件、有效期、confidence、資料快照。
- `decision`：人類批准人、批准時間、否決原因、例外理由。
- `paper_order`：order type、limit、size、期限、事件窗限制。
- `paper_fill`：下一個可成交 bar、滑點、費用、流動性拒絕原因。
- `position_lot`：逐 lot 成本、持有期、MAE/MFE、退出原因。
- `experiment`：假設、主要指標、比較基準、試驗次數、預先定義的通過門檻。

同一個 state machine 應同時服務回測與未來紙面交易，避免研究程式和執行程式各自解讀規則。每次 signal 產生時，必須凍結當時可見數據，日後修訂資料不能改寫舊決策。

#### 建立測試金字塔

- 單元測試：indicator、symbol mapping、時區、調整價、缺失資料、止損狀態機。
- 契約測試：每個資料源的欄位、型別、單位、排序、日期範圍與降級行為。
- property-based tests：OHLC 關係、日期單調、價格非負、volume 規則。
- golden dataset：固定少量 A/H/US 標的與已知 corporate action，結果不可漂移。
- 故障注入：timeout、403、截斷 JSON、空回應、429、程序中止、磁碟滿。
- end-to-end replay：由原始抓取到 signal、order、fill、position、report 全鏈重播。

CI 應禁止「測試數為 0 仍成功」這類假綠燈。現有 `unittest discover` 曾因測試檔採自訂執行方式而顯示 0 tests，但直接執行才得到 11 tests passed；CI 需明確固定測試 runner 及收集規則。

### P2：八至十二週驗證

#### 先測最簡策略

不要一次回測全部 C/R/N/D/K/W/G 規則。先選三個最核心、最常觸發、最容易客觀定義的規則族：

1. P0 突破確認制。
2. MA 滑動退出／減倉制。
3. 事件窗只減不加制。

每個規則都要與簡單基準比較，例如 buy-and-hold、MA-only、固定止損和不使用事件窗。結果必須按市場、年份、波動 regime、流動性組別和持有期分層，不可只報全樣本平均。

#### 回測最低規格

- Point-in-time universe，避免 survivor bias。
- Corporate actions、delisting、交易日曆、時區及收盤錨正確。
- 信號於收盤確認者，最早只能用下一個可交易時點成交。
- 加入佣金、稅費、bid-ask spread、滑點與成交量容量限制。
- Walk-forward／rolling out-of-sample，不隨機打亂金融時間序列。
- 為重疊標籤使用 purging／embargo，減少資料洩漏；相關研究顯示這些方法可降低泛化誤差。[^26]
- 登記每次參數／規則嘗試，計算 DSR、PBO 或至少 multiple-testing 調整。[^19][^16]
- 用 bootstrap 信賴區間，不只報單一 Sharpe。

#### 主要驗收指標

| 類別 | 指標 |
|---|---|
| 回報 | CAGR、總回報、相對 benchmark alpha、hit rate |
| 風險 | 最大回撤、Expected Shortfall、downside deviation、time-under-water |
| 交易品質 | expectancy、profit factor、MAE/MFE、平均持有期、turnover |
| 成本敏感度 | 基準、2 倍滑點、5 倍滑點下的淨回報 |
| 穩健度 | 樣本外 Sharpe、bootstrap CI、DSR、PBO、parameter stability |
| 可執行性 | 容量、流動性拒單率、gap-through-stop 比率 |
| 決策價值 | 與簡單基準相比的增量，不是絕對漂亮數字 |

任何規則進入實盤候選前，應預先寫下 go/no-go 標準。若測完後才決定甚麼叫「成功」，就會重新引入裁量偏誤。

### P3：治理與 AI

建立 AI Use-Case Register，把「摘要」「事實抽取」「研究生成」「訊號建議」「風險監察」「交易指令」按影響程度分級。NIST AI RMF 建議以 Govern、Map、Measure、Manage 貫穿 AI 生命週期，並持續追蹤已知及新興風險。[^27][^28][^29]

每個高風險用例要有 model card／system card：目的、禁止用途、資料範圍、提示詞版本、模型版本、評測集、已知限制、人工批准點、停止使用條件。SFC 明確要求投資研究類 AI 具有 senior management oversight、fit-for-purpose 評估、驗證、變更後重驗及持續監控。[^30][^13]

建立 100 至 300 個固定「投研黃金題」作 regression suite，至少包括：代碼混淆、幣種、復權、時區、事件日期、過期資料、同源新聞、衝突來源、虛構引用、止損優先級與倉位上限。評測不只看答案流暢度，而要量化：事實正確率、引用可追溯率、未知時 abstention、規則衝突率、數值重算一致率及 human override rate。

## 組織重設

### 四道關卡

| 關卡 | 擁有人 | 輸入 | 通過條件 |
|---|---|---|---|
| Data Gate | 數據腿 | 原始資料、source、hash、DQ 報告 | 新鮮度、完整度、一致性、corporate action 全通過 |
| Research Gate | 宏觀／量化 | 假設、證據、反證、預期 horizon | 預先定義 thesis 與 invalidation；禁止只寫方向 |
| Validation Gate | 獨立驗證／紅隊 | point-in-time replay、試驗冊 | 樣本外、成本、DSR/PBO、基準增量合格 |
| Risk Gate | 首席＋人類管理员 | 倉位、相關性、事件風險、例外 | 符合風險預算；人工簽署；有 kill switch |

「首席」不應同時負責創建規則、挑參數及宣布驗證成功。規模未足以設專職驗證人員時，可採輪值紅隊，但驗證報告必須在不知道原建議腿身份和方向的情況下完成。

### 衝突與例外

每項裁定加入 reason code，而不是只寫自然語言。建議分類為 `DATA_CONFLICT`、`MODEL_DISAGREEMENT`、`RISK_CAP`、`EVENT_BLOCK`、`STALE_SIGNAL`、`HUMAN_OVERRIDE`、`EXECUTION_FAILURE`。

任何人工 override 必須記錄：原始建議、修改內容、責任人、時間、原因、期限及事後結果。三個月後可分析哪些 override 增值、哪些只是情緒或事後合理化。

## 數據架構目標

建議採 Bronze／Silver／Gold 三層：

- Bronze：原始不可變回應，保存 provider payload、request timestamp、URL／endpoint 和 hash。
- Silver：統一 instrument_id、時區、單位、調整標誌和資料品質旗標。
- Gold：指標、特徵、訊號、風險暴露與報表，全部指向 Silver snapshot id。

CSV 可保留作交換格式，但歷史時間序列主儲存可轉 Parquet，配 schema registry 和 partition 策略。每個資料集應定義 owner、SLA、freshness、completeness、uniqueness、accuracy proxy、lineage 及 retention。

港股歷史 K 線目前依賴騰訊單源，16 條備援曾全部失效；AAStocks 只提供實時資料。解法不是再加入一堆不穩定免費源，而是選一個有 SLA 的第二歷史源，持續做 shadow comparison，並保存每日本地冷備。

## 規則治理目標

建立單一 `rules.yaml`／資料庫：

```yaml
rule_id: P0
version: 1.3.0
status: active
owner: quantitative
scope: [US, HK, CN]
inputs: [close, volume, ma20]
logic: machine-readable expression
parameters:
  volume_multiple: 1.5
  confirmation_days: 3
entry_effective: next_tradable_bar
invalidation: explicit conditions
validation_report_id: EXP-2026-001
approved_by: human-admin
supersedes: P0@1.2.0
```

規則變更必須使用 semantic versioning：文字澄清改 patch；參數改 minor；邏輯或適用範圍改 major。舊規則不可覆寫，只能 retired；所有報告以 rule ID + version 引用。

現有 24 組重複檔案應由一份 canonical artifact 加 alias/index 取代。全文檢索可使用 metadata catalog，但 AI 檢索預設只取 `status=active` 及最新 approved 版本，避免讀到凍結或草稿。

## 風險模型補強

目前的單標的、主題、加密及總闸是好開始，但屬名目上限。下一步應補：

- 風險貢獻：按 volatility、beta、correlation 計算 marginal contribution to risk。
- 因子暴露：AI／半導體／利率 duration／中國 beta／美元／商品等 look-through exposure。
- 流動性：ADV participation、days-to-liquidate、gap risk。
- 壓力測試：10Y 上升、VIX 跳升、港股流動性衝擊、AI 鏈共同下跌、資料源中斷。
- Drawdown policy：組合級警戒、降風險、停止新增及 kill switch。
- 模型風險：資料 stale、模型不可用、AI 回答不一致時，自動降級為 no-trade。

IOSCO 指出的核心 AI 金融風險包括模型和資料、第三方集中、外包依賴，以及人機互動問題；這些風險應像市場風險一樣進入風險總表，而不是只放在 IT 附錄。[^31][^32]

## 12 週路線圖

| 時間 | 必做 | 可驗收產物 |
|---|---|---|
| 第 1 週 | key 輪換、外部 watchdog、告警、資料 freeze | incident drill 通過；無秘密殘留 |
| 第 2 週 | Manifest v2、schema registry、原子寫入 | 任一 CSV 可重現和驗 hash |
| 第 3 週 | instrument master、symbol history、corporate actions | XOM/CVX、港股代碼等案例自動攔截 |
| 第 4 週 | Rule Registry、append-only ledger schema | 100% active 規則有 owner/version/status |
| 第 5–6 週 | event-driven replay 與成本模型 | P0/MA/event-window 可端到端回放 |
| 第 7–8 週 | walk-forward、purge/embargo、試驗登記冊 | 首份 OOS 驗證報告及基準比較 |
| 第 9 週 | DSR/PBO、bootstrap、壓力測試 | 明確 pass/fail，不只報平均回報 |
| 第 10 週 | AI 黃金題與紅隊評測 | 每版模型可比較，重大退化會阻擋發布 |

| 第 12 週 | readiness review | 由人類决定繼續 paper、延長 shadow，或極小額試驗 |

## 實盤准入門檻

在下列條件全部達成前，不建議自動或半自動真金白銀執行：

- 至少 6 至 12 個月連續影子運行，具體長度按訊號頻率及樣本量決定。
- 核心規則通過樣本外、成本、壓力及多重測試調整。
- 所有輸入都有 point-in-time lineage，沒有未分類空白。
- scheduler、資料源、AI provider 任一失效時預設 no-trade。
- 每筆交易都有硬性最大損失、組合風險預算及 kill switch。
- 人類管理員保留最終批准；AI 不持有券商密鑰，不可繞過風險閘。
- 完成交易前合規、稅務、資料授權與牌照適用性評估。

SEC 已公開警告投資者不要依賴 AI 生成資料預測市場，應驗證底層來源並查閱多個來源；SEC 亦曾因投資顧問誇大 AI 能力而採取執法行動。對外描述這套系統時，應準確稱為「AI 輔助、人工終審、紙面驗證中的研究與風控流程」，不要稱作已驗證的 AI 交易系統。[^33][^34]

## 最終取捨

短期不應把資源放在更多指標、更多角色或更漂亮的 HTML 報告。首要目標是減少自由度、固定資料與版本、建立反事實基準，然後用可重複試驗判斷哪些規則真正增值。

建議投資順序是：**可靠數據與 lineage → 統一台賬／執行引擎 → 樣本外驗證 → 獨立紅隊 → 風險模型 → 極小額受控試驗**。這個次序能保留現有系統最有價值的紀律與治理，同時補上目前最欠缺的證據、工程及問責閉環。
